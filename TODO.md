All three planned APIs implemented per `draft-implementation-plan.md` §6. Open-Meteo and

- [x] ~~Open-Meteo: low-risk contextual data (cloud cover)~~ ✅ done 2026-08-11 — `src/lib/events/adapters/openMeteoWeather.ts` (+ `.test.ts`), wired into `/api/feed/route.ts` as a 4th source. Samples one point per theater (`ConflictConfig.client.mapCenter`), not every city, deliberately kept low-volume. `type: 'WEATHER_CONTEXT'`, `severity` always `'info'`, `location.precision` always `'regional'` — inert against every correlation rule by design. Verified end-to-end against the real live Open-Meteo API (not just fixtures) via a dev-server smoke test.
  - CORS gate: satisfied by architecture (server-side fetch only, same as every other adapter) — no new code, documented in the adapter's doc comment.
  - Rate-limit gate: upstream 429 → `'rate-limited'` (existing convention) plus a **new** self-throttling in-memory TTL cache (15 min default) inside the adapter — the first adapter in the repo to cache, since `/api/feed` has no per-adapter poll-interval control and weather changes far slower than the feed's ~120s poll cadence.
  - Geographic precision gate: event `location` uses Open-Meteo's own *echoed* lat/lon, not the query input (the API grid-snaps to its model resolution).
- [x] ~~USGS: earthquake data, to be labeled "Seismic Activity"~~ ✅ done 2026-08-11 — `src/lib/events/adapters/usgsEarthquakes.ts` (+ `.test.ts`), wired into `/api/feed/route.ts` as a 5th source. Reuses `server.firesBBox` for theater scoping (same theater extent already used to scope FIRMS, despite the fires-specific name). `type: 'SEISMIC_ACTIVITY'`, `location.precision: 'exact'` (a real instrumented epicenter, unlike Open-Meteo's sampled-point `'regional'`), `confidence` reflects USGS's own `reviewed`/`automatic` review status. Non-earthquake feature types (e.g. `'quarry blast'`) are silently filtered, not surfaced as seismic activity. The flagged GeoJSON `[longitude, latitude, depth]` ordering footgun is guarded by an explicit regression test and commented destructuring — verified correct against a **real live M4.7 earthquake near Iran** returned by USGS during the dev-server smoke test (non-swapped coordinates, sane place name/depth).
  - CORS gate: satisfied by architecture, same as every other adapter.
  - Rate-limit gate: upstream 429 → `'rate-limited'` only — deliberately **no** self-throttling cache here (unlike Open-Meteo): USGS's own feed already refreshes on a cadence close to `/api/feed`'s ~120s poll interval, so a cache would rarely hit and wasn't worth the complexity.
  - Geographic precision gate: explicit lon/lat-order regression test + the standard post-Zod bbox filter.
- [x] ~~IODA: internet outage detection, "pending strict geographic validation"~~ ✅ done 2026-08-11 (implementation) — `src/lib/events/adapters/iodaOutages.ts` (+ `.test.ts`), wired into `/api/feed/route.ts` as a 6th source. `ServerConfig.iodaCountries` (new field) reuses the exact same belligerent country sets already encoded in `countryAttribution` (Iran/Israel/Lebanon/Syria/Yemen; Ukraine/Russia/Belarus) rather than inventing a new list. Queries one country at a time via `/outages/events/country/{code}` (`Promise.allSettled`, mirroring `googleNewsConflict.ts`'s multi-query shape — IODA has no bbox/lat-lon query, unlike every other Phase 4 adapter). A small static `COUNTRY_INFO` table supplies representative coordinates/names (`location.precision: 'regional'`, and `location` is omitted entirely for any country code not in the table — never fabricated). `severity` is deliberately fixed at `'medium'` for every event rather than banded from IODA's `score` field, which is unbounded/uncalibrated with no real data available to set sane thresholds against — banding it would have been exactly the false precision this project's hedging policy warns against.
  - ⚠️ **Not independently live-verified**, unlike Open-Meteo/USGS. Found IODA's real API spec via CAIDA's own GitHub wiki (`github.com/CAIDA/ioda-api/wiki/API-Specification`), but this sandbox's network egress reaches `open-meteo.com`/`earthquake.usgs.gov` fine while `api.ioda.caida.org` connections time out (DNS resolves, TCP connect hangs — an egress allowlist, not IODA being down). Confirmed with the user, who chose to proceed building defensively against the documented spec rather than block on network access. **What *was* verified live**: the graceful-degradation path — a real dev-server hit to `/api/feed` against the actually-unreachable IODA host confirmed the route still returns `200` in ~11s (bounded by the adapter's own 10s per-request timeout, not hanging) with the other 5 sources `healthy` and `ioda-outages-iran-israel` correctly self-reporting `unavailable`. **What was not verified**: the happy path — whether the documented `{ error, data }` wrapper shape and `{ datasource, entityType, entityCode, from, until, score }` item shape actually match live responses. First thing to check if a future session with real network access sees this source stuck on `invalid-response`.
  - CORS gate: satisfied by architecture, same as every other adapter.
  - Rate-limit gate: upstream 429 → `'rate-limited'`, plus the same self-throttling TTL cache pattern as Open-Meteo — justified even more here, since this adapter makes *N* outbound calls per fetch (one per country) and there's no confirmed sense of IODA's real rate-limit posture.
  - Geographic precision gate: country-code → coordinate mapping is a static, bounded lookup table (never fabricated for an unmapped code), `precision` always `'regional'` (a whole-country signal, not a point location).
- [ ] No incoming-request rate-limiting or CORS middleware exists anywhere in the repo (confirmed via repo-wide grep). Deliberately not built — `CLAUDE.md`'s Environment section states this is a local-only, unhosted dev tool with no auth, so generic request-throttling infrastructure would defend against a threat model that doesn't apply. Revisit only if the app is ever actually hosted publicly.
